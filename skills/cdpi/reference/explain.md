# Explain: the DPI ideas

Answer from these points, cite the page, and run `cdpi show <page>` when more detail is needed.

## Core ideas

- **An approach, then examples.** DPI is first an approach: minimal, reusable, interoperable blocks plus governance,
  so that others can innovate at scale. Only then is it a list of real systems
  ([What is DPI?](https://docs.cdpi.dev/the-dpi-wiki/what-is-dpi)).
- **Rails, not apps.** It follows the model of the Internet and mobile networks: open protocols
  (TCP/IP, HTTP, SMTP, GSM) that triggered public and private innovation. It moves from platforms to protocols
  ([DPI Overview](https://docs.cdpi.dev/the-dpi-wiki/dpi-overview)).
- **Three block families.** Identity and trust. Data sharing and credentials. Payments and transaction networks.
  These are necessary but not sufficient.
- **Three parts of every ecosystem.** Technology architecture, transparent governance, and market innovation
  ([DPI Overview](https://docs.cdpi.dev/the-dpi-wiki/dpi-overview)).
- **DPG ≠ DPI.** Open-source digital public goods can build DPI. So can proprietary software, if it implements open specs.
  Open source is a benchmark, not a requirement ([DPG and DPI](https://docs.cdpi.dev/the-dpi-wiki/dpg-and-dpi)).
- **Maturity, not yes/no.** A system grows into infrastructure as others reuse it
  ([Is my system a DPI?](https://docs.cdpi.dev/the-dpi-wiki/is-my-system-a-dpi)).
- **Conviction, not deep pockets.** Many blocks are small +1 additions to existing systems
  ([Cost](https://docs.cdpi.dev/the-dpi-wiki/how-much-does-it-cost-to-build-dpi)).

## The four myths, as engineering claims

| Objection | CDPI's answer | Holds only if |
|---|---|---|
| [Adoption needs a mandate](https://docs.cdpi.dev/mythbusters-and-faqs/dpi-and-mandating-adoption) | Usually not. Mandates produce checkbox integrations that collapse when the policy changes | Each adopter gets immediate value. Reciprocity rules where data flows both ways |
| [Shared rails mean surveillance](https://docs.cdpi.dev/mythbusters-and-faqs/dpi-and-privacy-security) | Good design gives users more control | The system really has minimal fields, no purpose or location tracking, per-system tokens, federation, yes/no queries and signed, revocable consent. Check these, don't assume them |
| [Public rails crowd out builders](https://docs.cdpi.dev/mythbusters-and-faqs/dpi-and-private-competition) | "Public" means public interest, not public ownership. Rails grow the pie | Access stays open on equal terms and the rail owner doesn't also build every app |
| [Digital excludes people](https://docs.cdpi.dev/mythbusters-and-faqs/readme) | DPI is not digitisation | Offline, low-bandwidth and assisted modes actually ship |

## Execution habits worth stealing

From the [21 suggestions](https://docs.cdpi.dev/the-dpi-wiki/dpi-implementation-and-execution-guidance):
- Frame the real problem and map why incumbents act as they do.
- Start with a coalition of the willing.
- Keep teams small, with high ownership.
- Run phases in parallel.
- Test early in sandboxes.
- Don't charge on day 1.
- Build governance from the start.
- Minimise your own role.

For a first use case, pick something people use often or a big pain point, with wide reach and an owner who agrees.
Run three candidate use cases and three first adopters in parallel
([First use case](https://docs.cdpi.dev/the-dpi-wiki/first-use-case-for-dpi)).
